# Decision: Layer 1 APSU behavior in 26.6

**Status:** Decided
**Release:** 26.6
**Summary:** 26.6 goes back to the Layer 1 APSU behavior that shipped in 26.5.

## Decision

APSU's on/off state depends on the SerDes lane rate and on whether ILT (link training) is on.

| SerDes lane rate | ILT on | ILT off |
|---|---|---|
| 212G (e.g. 1.6T-R8, 800G-R4) | APSU **on** | APSU **off** |
| 106G | APSU **off** | APSU **off** |
| 53G *(future)* | APSU **off** | APSU **off** |

- **212G SerDes:** APSU stays off when ILT is off and turns on when ILT is on.
- **106G SerDes:** APSU is always off.
- **53G SerDes (future):** APSU is always off.

## Implications

- The per-resource-group **"Enable APSU when no ILT"** checkbox no longer turns APSU on
  while ILT is off on 212G ports. A 212G link without link training (for example,
  1.6TBASE-CR8 copper running at a fixed setting) comes up without APSU, just as in 26.5.
- To get APSU on a 212G port, turn ILT on.
- If a 26.6 test plan or config assumed APSU without ILT, re-check it.

# Proposal: APSU control in the 27.0 UI

**Status:** Proposed
**Release:** 27.0
**Team input:** Keep a forced **On** option (APSU without ILT).

## Problem with the current UI

The **"Enable APSU when no ILT"** checkbox on each resource group is unclear once the 26.5/26.6 behavior is in place:

1. On 212G SerDes, APSU follows ILT, so the checkbox can be ticked and still have no effect.
2. It appears on 106G (and future 53G) modes, where APSU is never available.
3. ILT is set somewhere else, often per port, so this screen never shows whether APSU is actually running.
4. "when no ILT" is a negative condition that the user has to work through in their head.

## Proposed control

Replace the checkbox with an **APSU** dropdown on each resource group and show the effective state per port.

| Option | Behavior | Shown for |
|---|---|---|
| **Auto (follows ILT)** *(default)* | APSU on when ILT is on, off when ILT is off. Same as 26.5/26.6. | 212G modes |
| **Off** | APSU never runs. | 212G modes |
| **On (forced)** *(advanced)* | APSU runs whether or not ILT is on. | 212G modes |

On 106G and 53G modes the dropdown is greyed out at **Off**, with the tooltip *"APSU is not supported on 106G SerDes."*

```
Resource Group 3
  Mode:  2 x 1.6T-R8-HD PAM4 212G
  APSU:  [ Auto (follows ILT) ▾ ]          Auto | Off | On (forced)
         Effective: Port 5 – On (ILT on)    Port 6 – Off (ILT off)

Resource Group 4
  Mode:  2 x 1.6T-R8-HD PAM4 212G
  APSU:  [ On (forced) ▾ ]  ⚠ APSU forced on without link training
         Effective: Port 7 – On (forced)    Port 8 – On (forced)

Resource Group 1
  Mode:  8 x 100G-R1 PAM4 106G
  APSU:  [ Off ▾ ]  (greyed)  ⓘ APSU is not supported on 106G SerDes
```

### UI rules

- **The default is Auto.** If the user doesn't touch the setting, they get the decided 26.5/26.6 behavior.
- **Forced On is clearly marked.** Put it under an "Advanced" label or show a warning icon, so it is never selected by accident.
- **The effective state is always visible.** Show one line per port under the control and add an **APSU** column (On / Off) with the reason (*ILT on*, *ILT off*, *forced*, *not supported*) in the port/link status view.
- **Tooltip:** *"APSU (receiver auto-adaptation). Auto: runs when link training (ILT) is on. On (forced): runs even without ILT. Supported on 212G SerDes only."*
- **Changing the mode re-checks the setting.** If a resource group set to Auto or On switches to a 106G mode, the control drops to Off and shows a note. Switching back to 212G restores the earlier choice.

## API / config compatibility

- Add an enum attribute, `apsuMode = auto | off | on`, and deprecate the old boolean.
- When loading a pre-27.0 config:
  - The old boolean **true** (`Enable APSU when no ILT` ticked) maps to **`on`** (forced), which keeps what the user asked for.
  - The old boolean **false** maps to **`auto`**.
- Log a deprecation warning when a script sets the old boolean.
- Setting `on` or `auto` on a 106G or 53G resource group gives a validation error. Don't accept it silently.

## Open items

- Confirm that forced On is allowed with every 212G mode, both copper (CR8) and optical (DR4/DR8).
- Confirm whether the per-port effective state can be read back from hardware or must be computed from the configuration.
